# Illustrated flipbook video

Shared browser implementation for the explicitly selected `illustrated-flipbook` knowledge-video presentation. The normal photo album template and other video styles keep their existing contracts.

The renderer consumes a validated `knowledge-video-flipbook-v1` manifest. Each spread binds one no-cat Ian/ImageGen complete raster, one exact `static_spread` narration body, audio-derived UTF-8 reveal ranges, persisted image/text sides, and an approved real `book-page-turn`. Source image and narration SHA-256 values are verified on disk before building. Source dimensions are measured and retained; landscape images allow a maximum `0.5%` relative deviation from `16:9`. The image displays at a logical width of `708` pixels and proportional height (`398.25` pixels for exact `16:9`) on the final `1920×1080` canvas.

An explicitly selected opening may add `opening_cover: {image: {path, checksum_sha256, width, height}, hold_frames: 24, open_frames: 30}`. The complete landscape cover uses `contain` and may include a cat; the no-cat rule still applies to every body spread. The cover holds for 24 frames, opens as a real hard page for 30 frames, and settles the camera before `S01` narration starts at frame 54. Without this selection, `S01` still starts at frame zero. Total frames include the selected opening. Recording proof binds the measured cover and body engine page indexes, the cover hold/open/completion events, the settled camera transform, and each ordinary page completion to the exact timeline.

Use `buildFlipbook(input, outputDirectory, {productionPreflight})` through the assembly adapter for production. `productionPreflight` is an executing synchronous gate, not a passed-in approval result. A production manifest includes its root-relative `episode_workspace`; `outputDirectory` must be its new `docs/flipbook-<id>` directory. The returned `build_descriptor` is under `schema/`; JS/CSS/vendor JavaScript live under `script/`, the vendor license remains in `docs/`, and recorded WebM lives under `assets/video/`. Call `createFlipbookServer(build_descriptor, {productionPreflight})`; the server verifies all current bytes and reruns the gate at startup and every recording mutation. The virtual website paths map to those categorized files.

The CLI accepts dedicated maintenance fixtures: generated synthetic fixtures, or explicitly authorized independent image copies with the preview provenance below. A local demonstration can be prepared without reading episode data or downloading dependencies:

```sh
node leverage-video/src/shared/flipbook-video/fixtures/synthetic.mjs leverage-video/src/shared/flipbook-video/fixtures/generated/demo
node leverage-video/src/shared/flipbook-video/build-flipbook.mjs leverage-video/src/shared/flipbook-video/fixtures/generated/demo/input.json leverage-video/src/shared/flipbook-video/fixtures/generated/demo-site
node leverage-video/src/shared/flipbook-video/serve-flipbook.mjs leverage-video/src/shared/flipbook-video/fixtures/generated/demo-site
```

An independent-image preview remains `action_classification: project_maintenance`. Replace the entire `fixture_provenance` with `knowledge-video-maintenance-preview-provenance-v1`: `synthetic: false`, `narration_kind: synthetic-script-test-only`, `image_kind: user-requested-independent-copies`, `production_eligible: false`, `episode_runtime_dependency: false`, `scope: visual-browser-recording-preview-only`, and the SHA-256 of the separately retained authorization evidence. Optional `audio_kind` and `system_voice` describe the actual synthetic-script audio provider. Do not retain `episode_data_used: false`, original file paths, or claims that imported images were generated for the fixture.

Each spread binds `image_provenance: {kind: independent-user-requested-copy, copy_checksum_sha256, white_cat_present: false, generation_claim: none}`. Image and narration paths still remain inside `leverage-video/src/shared/flipbook-video/fixtures/`. An optional opening cover is covered by the same top-level authorization and independent-copy provenance; its image checksum binds the copied cover bytes. Copy input images into fresh neutral filenames first; source symlinks and hard links are forbidden for both covers and body images. The renderer receives only the independent copy paths and checksums, never an original episode path. Production still requires its complete production preflight, body images remain no-cat, and all frame, text, image-dimension and recording checks remain required. Preview provenance cannot authorize production or promote a preview into a production delivery.

The default demonstration audio is an explicitly labeled test tone. To create a spoken synthetic fixture, pass an already installed macOS voice name, such as `Tingting`, as the generator's second argument. This invokes local `say` and existing `ffmpeg`, measures actual PCM samples for each phrase, and reserves silence for turns. It never changes the production voice provider or downloads a voice. The generator refuses a missing voice rather than switching providers.

Computer Use requires the user's explicit permission for the Codex internal browser. After that permission and the video workflow gates, open the printed loopback URL in the actual visible browser, use a `16:9` viewport, and click the recording button. Select that same tab. The runtime verifies Capture Handle, browser surface, source resolution, font/image readiness, exact text, overflow, and stable layout. It hides all outer controls before recording the wall-clock timeline. It refuses unsupported capture rather than switching rendering backends.

The default `captureMethod: 'cursor-never'` checks the result of `track.applyConstraints({cursor: {exact: 'never'}})` and the actual track setting. Resolving the promise while still reporting `motion` is a failure. The diagnostic button reports support, capabilities, initial settings and the actual result in visible DOM; stream acquisition times out after 15 seconds and constraint application after 3 seconds. Late streams are stopped. Earlier Codex internal browser trials retained `motion` and rejected Pointer Lock while the host browser's actual visibility was false, even though the document reported focus, visibility and a trusted active click. These background failures do not establish lack of foreground API support. Activate the task and expand its browser, then verify actual browser visibility before a foreground retry; that capability remains unverified until the real retry succeeds.

For the separately authorized independent-copy maintenance preview only, `buildFlipbook(..., {captureMethod: 'pointer-outside'})` prepares the shared current tab and waits for the user to move the pointer outside the browser viewport. A trusted document `pointerleave` or `mouseleave` with coordinates outside the viewport hides the controls immediately; capture starts only after a one-second stable interval and actual decoded-frame checks. A trusted reentry aborts the recording and stops every stream immediately. Proof retains the real `motion` setting and the observed leave coordinates/timestamps. `captureMethod: 'pointer-lock'` is also an explicit preview option: a button requests a real lock, waits six seconds, then focuses a second button for a fresh Enter gesture; Escape, lock loss, failure and completion release resources and restore the pointer. Neither option grants permission to operate an application, and neither is enabled for production. Production recording in this tested browser has not been verified end to end.

Normal capture uses `cursor_suppression.method: cursor-never`: the exact constraint must resolve, and the browser must report `never` after negotiation, after a decoded frame, and at recording completion. An explicitly authorized independent-copy maintenance preview may be built with `pointerLockPreview: true`. Its proof uses the distinct `pointer-lock` method and retains the browser's actual cursor settings. The `video-stage` lock must cover the complete recording, provide a six-second escape notice before capture, and release afterward; loss of the lock or Escape aborts capture. Production continues to require `cursor-never`. The server binds the proof method to the reviewed build's `capture_method`.

The capture is a silent WebM. Its proof contains source settings, manifest hash, layout measurements, text reveals, actual renderer state/flip events, completion count, and timing drift. Pixel dimensions come from actual `requestVideoFrameCallback` metadata and the video element, not transitional `getSettings()` values; the server requires an exact match with the encoded WebM dimensions. The server preserves the original WebM and proof, probes and fully decodes it, then writes a capture lock. The common assembly workflow aligns actual source `captureTime` observations with WebM packet timestamps before normalizing to exact `1920×1080`, 30 fps and the locked frame count. Any terminal extension is limited to 150 ms of an already fully revealed final hold; it cannot change the approved body, reveal or transition schedule. The locked narration and approved sound/caption roles are then muxed and visually audited. Renderer event times alone do not prove encoded pixels were presented on time, and a capture lock does not claim production delivery.
