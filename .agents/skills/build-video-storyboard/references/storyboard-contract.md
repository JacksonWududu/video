Before final storyboard QA, write a versioned transition-selection proposal bound to the draft storyboard and `scene-transition-catalog-v3`. Include exactly one ordered selectable row for each ordinary outgoing boundary and separately list the fixed opening hard cut and terminal clean hold as non-selectable exemptions. Hash the canonical presented mapping separately as `presented_map_sha256`; also record the full artifact's current file SHA-256 after every state update.
- Present each row's `source_shot_id → next_shot_id`, deterministic base recommendation, final diversified recommendation, required options, duration/frames (`0` for `cut`; 0.3–0.6 seconds for visible effects), adjustment reason, and semantic reason. Also present the mechanically derived per-kind cap and resulting counts. The user may approve the complete checksum-bound table at once or decide rows incrementally. Store unresolved rows as `pending`; preserve decided rows without silently changing them.
- If one user message both revises the global recommendation policy and names exact boundary choices, archive the exact message, time, prior `presented_map_sha256`, and ordered choices as `transition-review-user-request-v1`. Apply those choices while rebuilding the candidate and validate them against the new diversity limits, but keep their new rows pending until the rebuilt complete map and checksum are re-presented; the request is not approval of unseen downstream recommendations.
- General authorization or instructions such as `默认`, `你看着办`, or `继续` do not approve an unseen or unresolved transition. `确认全部推荐` is accepted only when the exact complete mapping and its checksum were already presented.
- A requested Remotion effect outside the active shared catalog is a blocker until the shared registry, renderer, tests, and validator consume it. Re-present the affected boundary after support exists; never replace it with a similar effect.
- Lock each ordinary row only with `user_selection.status: approved`, exact user message/time, and `presented_map_sha256`; after all rows pass, set phase `transition_review_approved`. The final storyboard's transition mapping must equal the approved review artifact exactly before Storyboard Review may begin.

## User-visible workcard and production handoff

Expose exactly two workcard artifacts in both the standard and revoice routes:

1. the final storyboard containing the exact corresponding narration in every shot;
2. the validated final narration audio resolved from the approved topic folder, or the validated replacement narration master for the active revoice variant.

Keep research packages, claim-evidence maps, source-audio archives, derived working audio, transcripts, comparison evidence, QA reports, and prompt logs internal to the episode project.

In the standard route, use this exact order: `storyboard_construction → awaiting_visual_direction_review → visual_direction_review_approved → awaiting_transition_review → transition_review_approved → storyboard_qa_passed → awaiting_storyboard_review`. When both workcard artifacts exist, Visual Direction Review and Per-Boundary Transition Review are fully approved, and visual-direction-selection binding, checksum, Summary-table, transition-selection binding, narration-coverage, opening-schedule, timing-source, canvas, subtitle-normalization, and action-continuity-plan validation pass, recompute the storyboard file's exact-byte SHA-256 and atomically record the active path/SHA-256 with phase `storyboard_qa_passed`. Before presentation, atomically write `storyboard_review.status: pending`, phase `awaiting_storyboard_review`, and the presented path/SHA-256 and presentation message/time in `schema/episode-state.json`; archive prior approval evidence in the superseded records and clear the active approved-version slot. Then present the complete storyboard script and validated narration audio and pause. On a change request, atomically set `changes_requested` and phase `storyboard_construction`, archive and clear active approval evidence, and only then edit. If a white-cat decision, structure, treatment, route, or compatibility changes, reopen its Visual Direction Review row, recompute and re-present the full direction map, invalidate that shot's visual family, and reopen affected Transition Review rows. If any boundary identity, kind, option, or duration changes, reopen only its Transition Review row before final QA. The new version must pass all validations, update active evidence with phase `storyboard_qa_passed`, return to `pending` and `awaiting_storyboard_review`, and be presented again. At explicit approval time, recompute the active file SHA-256 and require it to match the recorded active and presented SHA-256 before recording the approved path/SHA-256 and exact decision message/time and setting `approved` with phase `storyboard_review_approved`. Visual production may begin only while all three SHA-256 values, every visual-direction selection binding, and every transition-selection binding still match. In `revoice_variant`, use `revoice_storyboard_retiming → awaiting_revoice_storyboard_review → revoice_storyboard_approved`, preserve the checksum-valid parent-version transition evidence exactly, then return to the orchestrator for binding; visual production remains forbidden.

When revising a standard-route storyboard after visual work exists, emit a shot-level change set before touching `visual_asset_review`. Compare the prior and new visual contracts per shot; preserve every unchanged shot's exact image bytes, technical QA, pending-review status, and exact-byte approval evidence. Timing or narration-span changes may rebind existing bytes after semantic/timing QA when scene content, action-state count/order, framing, visible text, and asset mapping remain valid. Do not mark an entire queue inactive merely because the storyboard file SHA-256 changed. Replaced, removed, or visual-contract-changed shots alone become inactive or `superseded`, together with their true dependent family members. A batch review document or contact sheet whose membership changed must be rebuilt, but its unaffected member-image evidence stays valid.
