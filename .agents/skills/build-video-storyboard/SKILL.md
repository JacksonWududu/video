# Build Video Storyboard

Read [references/storyboard-contract.md](references/storyboard-contract.md) completely before drafting or validating the storyboard.
Read [../run-knowledge-video/references/visual-language-and-comic-routing.md](../run-knowledge-video/references/visual-language-and-comic-routing.md) completely before classifying visual structure/treatment/route or inspecting legacy Comic evidence.

## Preconditions

- Gate 2 passed and the exact user-approved script is locked.
- One checksum-current `white-cat-visual-style-selection-v1` is locked for the episode; density binds its SHA-256.
- The validated narration master exists, decodes cleanly, and has a recorded checksum and real duration.
- No earlier estimated timestamps remain authoritative.
- The episode canvas is locked to native `16:9`, `1920×1080` landscape at `30 fps`; plan framing and subtitle-safe areas for that canvas.

## Build from audio

1. Derive shot boundaries from complete semantic beats and natural pauses in the validated narration master.
2. Cover the complete locked script exactly once, in order, with no omission, addition, duplicated wording, or rewrite. Keep this exact narration as `source_text`; derive bottom-subtitle `display_text` only by removing every Unicode punctuation code point (`General_Category=P*`), then trimming and collapsing repeated whitespace.
3. Add the single `OPEN-00` row from `cover-only-v1`. It shows the exact shared cover from composition frame 0 through `first_sentence_end_frame` and carries the complete first narration sentence; narration-master and composition times are identical.
4. Write machine `scene_class` only as `narrative_illustration` or `structured_graphic`; use `structured_visual_kind` for data, comparison, cause/effect, or transition-graphic detail. Chinese scene labels are display-only. Derive compatible visual structure/treatment fields, resolve the structure-owned layout, and reject an `avoid` pairing.
5. Choose the knowledge carrier and make only a default recurring-cat recommendation with a rationale. When the cat is recommended, map the narration beat to its narrative role, visible action/result, and cognitive change; never use it as a decorative pointer or substitute it for a factual historical or experimental subject. This is not yet a final cat or route decision.
6. Derive compatible routes through `visual-generation-route-catalog-v2` and its validator. Keep `imagegen` as the default narrative route; expose `xuan-paper-diorama` as an explicit, non-default no-cat narrative alternative bound to the checksum-pinned `$generate-visual-styles` profile. Keep `ian-handdrawn-ppt` as the structured default, with checksum-pinned `ink-doodle-knowledge-card` as an explicit structured alternative. Every selected Ian shot must carry an exact `ian-layered-scene-plan-v1` whose ordered semantic layers cover the shot narration bytes once. Its layer count, semantic roles, and local entry frames must equal the approved visual-rhythm shot's `asset_plan.layer_count` and ordered `meaningful_change_events`, with `entry_frame = event.at_frame - shot_start_frame`. Expose `local-video-file` only as an explicit, never-default no-cat alternative for either scene class; it requires one absolute `.mp4` path per shot, `source-video-native`, and no added visible text. A comic treatment remains an `imagegen` treatment; `comic-imagegen` is retired, as is `doodle-slides`, and neither may appear in a new or modified v3 choice. A retained white cat uses only `imagegen`, the canonical reference, and the Gate-2-selected treatment. Never recommend Whiteboard or local video by default or invoke any route before explicit approval.
7. Complete Per-Shot Visual Direction Review before the Complete Visible Text Batch Review. `OPEN-00` is the sole exemption: `white_cat_present: 不适用` and `visual_generation_route: 固定封面（cover-only-v1）`.
8. Derive visible-text candidates only as concise summaries under `concise-summary-visible-text-v1`. Build `visible-text-batch-review-v1` over every active generated shot, including `none` rows, present the complete ordered map once, and require one explicit whole-map user approval in both `manual` and `one_click`. Never request, accept, or store per-shot visible-text approval. A one-click policy cannot authorize this gate.
9. Only after phase `visible_text_review_approved`, build a `scene-transition-v3` proposal for every ordinary boundary. Resolve any matching rule declared by the approved source generation route first. Otherwise, when either endpoint is a white-cat `imagegen` shot, use the bound episode style: `loose-line-vivid-watercolor` applies `imagegen-white-cat-watercolor-bloom-priority-v1`; `twilight-neon-animation` applies `imagegen-white-cat-twilight-dissolve-priority-v1` with `dissolve`. Only when neither priority applies use the shared semantic fallback (`cut` for continuity, `match-cut` for match continuity, `dissolve` for section change, `paper-wipe` for route change with `wipe`/`from-left` when entering Whiteboard, `fade` for time/place change, and `wipe`/`from-left` for contrast or warning). Record the recomputed recommendation authority/rule ID, style ID, then apply `scene-transition-recommendation-diversity-v2`: `cut` is exempt; the same visible kind may occur consecutively at most three times; each visible kind may occur at most `min(5, floor(visible_count × 0.30))` times, using all visible ordinary boundaries as the share denominator. Diversify white-cat preferences and shared fallbacks deterministically when needed. Never replace a matching route-specific recommendation; fail closed if a route-owned recommendation or explicit user request violates the consecutive, absolute, or share limit. Record every adjustment and include the policy in the presented-map projection. Every selected kind/options must still exist in the active `scene-transition-catalog-v3`, use the shared renderer, and receive explicit review. `zoom-blur`, `flip`, `slide`, and `clock-wipe` are retired from v3 selection and recommendation; retain them only for unchanged historical v2 parsing/rendering. Registered `cut` uses zero seconds/frames and empty options; visible effects remain 0.3–0.6 seconds and default to 0.4 seconds/12 frames. Only `OPEN-00 → S01` is the fixed opening hard cut; only the terminal shot omits an outgoing transition.
10. For every new or replanned shot, require the explicit density selection and write checksum-bound `storyboard-visual-rhythm-v2`. Standard preserves existing counts. Rich stateful targets 4–6 and permits 2–6; 2–3 requires a complete allowed `density_fallback`. Rich hero uses one background plus 4–13 poses, targets 10–12 total assets, requires fallback at total 5–9, and requires no-split assessment plus quantity rationale at total 13–14. Bind density mode/selection SHA-256, fallback and split assessment into the canonical hash. Legacy v1 is read-only.
11. For every v3 `N`-image sequence, write exactly `N - 1` `intra-shot-transition-v1` entries. The default builder emits registered zero-frame `cut` for every adjacent pair. `watercolor-bloom` is optional only after the user explicitly approves that exact entry against the active visual-rhythm map; it remains fixed at 0.6 seconds/18 frames. A cut target needs at least 15 clean frames; a watercolor target needs 18 reveal frames plus 15 clean frames. Missing, `none`, unknown, stale, implicit, or renderer-unsupported effects block. Whiteboard and local video keep their named asset contracts and empty raster transition maps. Never use morph, optical flow, generated in-betweens, or frame interpolation.

## Add the opening Summary table

- Immediately after the storyboard document title, add `## 分镜 Summary` and the exact seven-column Markdown table header `| 镜头 | 时长（秒） | 画面 | 白猫 | 分镜生成方式 | 可见文字 | 锁稿原文 |`.
- Include every active row exactly once in storyboard order, including the single `OPEN-00` row.
- Copy each row's shot ID and visual description without summarizing or rewriting them. Render read-only duration as exact `(end_frame - start_frame) / 30` seconds with exactly three decimals; never derive it from rounded display timestamps. For `OPEN-00`, render white cat as `不适用` and route as `固定封面（cover-only-v1）`. For every other row, copy the exact approved `white_cat_present` and `visual_generation_route`; neither cell may be `待确认`, unknown, incompatible, or checksum-stale.
- Render visible text as the exact whole-batch-approved wording or `无` for mode `none`. A final storyboard must never contain `needs-confirmation` or `待确认`.
- Render the row's exact `source_text` in the locked-narration cell. Apply only the deterministic table-cell escaping defined in the storyboard contract.
- Treat the table as a review-only duplicate. Keep all existing detailed shot sections and authoritative fields unchanged, and exclude the Summary copy from narration-coverage concatenation.

## Require Per-Shot Visual Direction Review

1. After drafting every generated shot but before a transition proposal, write `schema/per-shot-visual-direction-review-v3.json` with `contract_version: per-shot-visual-direction-review-v3`, route catalog v2 and visual-language catalog v1 versions/checksums, draft storyboard path/checksum, and one ordered row for every generated shot. Exclude only `OPEN-00`.
2. Each row must contain machine scene class/structured kind, factual identity, white-cat recommendation, structure/treatment, active route compatibility/reasons, recommended route, and a visible-text candidate tuple. Until the schema cleanup, legacy Comic fields are fixed compatibility placeholders: eligibility/recommendation `false` and plan `null`; they are not selectable. Draft text may be `needs-confirmation`; a resolved candidate accepts only `none` or `required`. Resolve text by active route: `imagegen` with `white_cat_present: true` and every `xuan-paper-diorama` shot are forced to `none` with null copy/placement and no top title; every other active route uses its own text contract. A direction-row selection records the candidate but never constitutes visible-text approval.
3. At `awaiting_visual_direction_review`, present every current active storyboard row in the Summary-shaped `visual-direction-review-form-v3` surface `镜头｜时长（秒）｜画面｜白猫｜分镜生成方式｜可见文字｜锁稿原文` with immutable `presented_map_sha256`; the initial draft may contain 21 rows, but a structurally revised draft uses its actual active-row count. Keep duration, `锁稿原文`, and the whole `OPEN-00` row read-only. For generated rows expose editable non-empty 画面, white-cat yes/no, compatible active routes, and `none | required` visible text; `required` also requires exact copy and placement. A `local-video-file` row additionally requires a per-shot absolute `.mp4` path, forces no cat/no added text, and any path change rebuilds and re-presents the candidate map. Support full or selected submission plus compatible-only batch edits, but never bulk-assign local video because paths are shot-specific; report every skipped row/reason. The form sends storyboard-checksum-bound `visual-direction-form-submission-v3` through a Codex follow-up message and never writes episode files directly. A retained white cat may select only `imagegen`, with the Gate-2-selected treatment and cohesion binding. Cat removal/addition requires recomputation and re-presentation.
4. A user may decide manual scene/cat/route rows incrementally or use `确认全部推荐` only after the exact complete table and `presented_map_sha256` were presented; one-click may policy-authorize deterministic direction recommendations. Neither path approves the visible-text candidates. Do not interpret `默认`, `继续`, `你看着办`, general authorization, or Storyboard Review as a missing selection. Record direction authority separately from the immutable projection.
5. When every generated shot has a current compatible cat/route decision and every detailed shot field and Summary row match it, set phase `visual_direction_review_approved`. Do not enter the visible-text batch gate while any row is pending, unknown, incompatible, mismatched, or checksum-stale; do not enter Transition Review, Storyboard Review, or visual production before the separate whole-batch visible-text approval.

Validate every submitted form payload with `node leverage-video/src/shared/visual-direction-review-form/validate-submission.mjs <episode-workspace> <submission.json>`. A compatible route-only change may bind directly with the derived treatment (`xuan-paper-diorama`, `ian-handdrawn-technical`, `ink-doodle-knowledge-card`, `whiteboard-clean-progressive`, `source-video-native`, or compatible-current/fallback `imagegen-watercolor-narrative`); selecting local video still requires its exact absolute path and re-presentation. A 画面 change is never selection-ready: reopen that row, rebuild its semantic beat, scene class/kind, factual identity, cat recommendation, structure/treatment, route/text compatibility, framing, camera/motion/action family, detailed/Summary projections, and adjacent ordinary transitions, then regenerate storyboard and presented-map checksums and re-present it. A white-cat change reopens semantic and compatibility review; a visible-text or local-video-path change creates a new candidate direction map. Preserve unaffected direction choices, reopen only adjacent ordinary transitions, and synchronize detailed rows, Summary, review JSON, and state pointers. Any visible-text candidate change also invalidates the prior whole-batch approval and requires the complete visible-text map to be rebuilt and presented once.

The same form may send `storyboard-shot-merge-request-v1` only at `awaiting_visual_direction_review`. Require at least two generated shots that are contiguous in current active order, no dirty unsubmitted direction fields, the current storyboard SHA-256 and `presented_map_sha256`, and `renumber_strategy: compact_after_merge`. Validate it with `node leverage-video/src/shared/visual-direction-review-form/validate-merge-request.mjs <episode-workspace> <request.json>` before mutation. Keep the first selected ID as the merged survivor, compact every later generated ID, preserve uppercase padded `S` numbering, and record the complete old-to-new map without rewriting historical review files. Concatenate exact `source_text` with no inserted bytes and span timing from the first source start through the last source end. Apply `first-shot-visual-inheritance-v1`: preserve the survivor's complete scene/visual/cat/structure/treatment/route/text/camera/motion/action-family contract; ignore all later members' corresponding visual contracts. Validate that survivor contract unchanged, play its existing action family once over the original survivor span, then hold its final visual state across the appended span without deriving additional action states from the merged duration. Do not reject this named exception merely because the ordinary full-span required character-state count exceeds five; reject only if the preserved first-shot family or deterministic final-state hold fails its own checks. Remove internal boundaries, reopen the merged presentation binding plus every renamed downstream direction row and changed transition identity, refresh checksums, and re-present all active rows. `OPEN-00` and `revoice_variant` are never mergeable.

## Require Complete Visible Text Batch Review

1. After the current direction map is bound, derive one `visible-text-batch-review-v1` row for every active generated shot in storyboard order, including `none`. Bind the current storyboard path/SHA-256, direction path/file SHA-256/map SHA-256/status, exact mode/copy/placement, and locked-narration SHA-256. Use `batch_scope: complete_active_generated_shot_visible_text_map` and `row_approval_mode: forbidden_batch_only`.
2. A `required` phrase must pass `concise-summary-visible-text-v1`: one or two non-empty lines, no more than 28 non-whitespace code points total, no sentence-ending prose punctuation, and no registered colloquial address, filler, explanatory lead-in, or sentence-final particle. It should summarize the visual claim rather than repeat spoken narration. Mechanical checks enforce form; the human batch decision confirms semantic accuracy and concision.
3. Present the complete ordered map and immutable `presented_map_sha256`, set phase `awaiting_visible_text_review`, and stop in both approval modes. Accept one explicit approval of the whole presented digest. Store it only at the artifact top level with `scope: complete_presented_map`, `user_has_reviewed_complete_map: true`, and `row_by_row_approval_performed: false`. Any row-level approval/status/message/time field is invalid.
4. On approval set phase `visible_text_review_approved`. If any mode, wording, placement, row set/order, storyboard checksum, or direction binding changes, preserve the old artifact as superseded and re-present the complete new map once. One-click policy authorization and Per-Shot Visual Direction Review never substitute for this approval.

## Require Per-Boundary Transition Review

1. Only after phase `visible_text_review_approved`, create a versioned proposal with `catalog_version: scene-transition-catalog-v3` and one ordered row per ordinary boundary. Each row contains source/next IDs, routes, white-cat booleans, `boundary_change_class`, route-first, white-cat-priority, or shared-fallback recommendation authority/rule ID, deterministic base recommendation, `scene-transition-recommendation-diversity-v2` adjustment evidence, proposed kind/options, duration, and reason. Opening hard cut and terminal clean hold are fixed exemptions. Compute `presented_map_sha256` separately from the mutable artifact SHA-256, including the diversity policy and every adjustment.
2. Present the complete boundary table, diversity cap/counts, and available registered catalog entries before final storyboard QA. Reject a pending proposal with a visible-kind run longer than three, more than five uses of one visible kind, or a visible-kind share above 30%. A user may approve the complete presented mapping in one explicit message or decide rows incrementally; after a partial reply, preserve decided rows and present only the unresolved rows with their full choices.
   When the same user message changes the global recommendation policy and names exact boundary choices, bind those choices to the prior presented map as `transition-review-user-request-v1`, rebuild them into the new proposal as pending user-requested transitions, and re-present the checksum-current map before treating them as approved.
3. Do not interpret `默认`, `你看着办`, `继续`, general authorization, or later Storyboard Review as selection for an unresolved row. A phrase such as `确认全部推荐` is valid only after the exact complete mapping has been presented and its SHA-256 recorded.
4. If the user names another Remotion transition, verify that the exact kind and required options are present in the active shared catalog and consumed by the shared renderer. If missing, stop that row; extend and test the shared module first, then regenerate and re-present the proposal. Never substitute a different effect, silently discard an option, or record unsupported metadata.
5. After every row is decided, record the exact decision message/time and `presented_map_sha256`, set Transition Review to `approved`, and bind those exact fields into every detailed `scene-transition-v3` row. Only then run final storyboard QA.

## Plan character state families

- Use `action-state-schedule-v4` for new or replanned performing-character/core-object shots. It must match the v2 rhythm density/hash/count/fallback/split fields, exclude the hero background, contain exactly `pose_count - 1` intra-shot transitions, preserve unique semantic states and complete consecutive UTF-8 byte coverage, and prove `15 × N + transition frames` fits. Legacy v3 is read-only.
- Give every state a stable ID, unique non-empty semantic state, exact ordered UTF-8 narration byte range/text, and a real-audio semantic entry frame. The first state begins at frame 0; ranges are gap-free, non-overlapping, and cover the exact shot text once. States over 75 frames require a semantic hold reason.
- When more than five continuous states are proposed, first record a semantic split assessment. Only when no natural split exists may a user explicitly approve the exact shot/map hash; no silent expansion is allowed. A sixth `hero_pose` asset follows this path. A `stateful` shot never exceeds four states.
- Record goal, emotion, anticipation, main action, contact/weight, impact, recoil, follow-through, settled pose, environment response, facing, center-of-gravity shift, limb trajectory, and prop/accessory continuity. Every adjacent pair must be physically reachable and causally ordered.
- Keep camera, background, scale, lighting, and spatial relationships registered. Apply the approved `intra-shot-transition-v1` map: default `cut`; optional explicitly approved watercolor. Each target retains at least 15 clean frames after its incoming effect.
- If fewer than two independent complete-scene semantic states exist, do not label the shot `stateful`; use one-image `layered` or another route-specific asset contract. Whiteboard and local video never fabricate action states.
- `action-state-schedule-v2` remains unchanged history only: its one-to-five formula, 18–75-frame allocation, and mandatory adjacent watercolor continue solely for untouched v2 work.
- `first-shot-visual-inheritance-v1` preserves the survivor's already approved family and original active window, then holds the final visual state through the merged end. It creates no state, asset, or transition.

## Retime a completed revoice variant

Use `retiming-only` mode only with a passing parent storyboard, approved visual manifest, completed per-image approvals, exact locked script, replacement narration master, and `visual_sequence_lock`.

1. Copy the approved parent storyboard to a new versioned Markdown file; never edit it in place. Preserve its complete approved white-cat/route/structure/treatment/text mapping and checksum-valid `per-shot-visual-direction-review-v1`, v2, or v3 evidence. A parent containing retired `comic-imagegen` or `doodle-slides` is historical read-only and cannot enter revoice. Display and lock every other parent review without permitting a visual-contract change. A legacy parent still requires current-asset confirmation before revision; any requested visual change exits `revoice_variant`.
2. Treat v1/v2 as unchanged completed `legacy_read_only` evidence only. If any legacy shot is reopened outside strict revoice, write the affected current mapping as `per-shot-visual-direction-review-v3`; never append a new decision to a v1/v2 artifact.
3. Align each unchanged row's exact ordered script span to real timestamps in the replacement narration. Do not multiply old times by a duration ratio or estimate from reading speed.
4. Preserve row/shot IDs and order, exact `source_text`, semantic and visual fields, approved white-cat/route/text values, asset/state-family IDs and order, asset paths/checksums, crop/camera, internal-motion kind, and every parent transition's kind/options/duration seconds/duration frames/recommendation authority/selection evidence, plus cover and opening source. Never recompute action-state count or order. Preserve all Whiteboard bytes and checksums.
5. Recompute only narration in/out timestamps, shot/boundary placement frames, first-sentence end frame, cover hold, durations of existing state occurrences/internal motion, and existing sound-effect cue times. Never change an inter-shot transition duration or frame count. For Whiteboard, map each locked annotation element's exact subtitle span to a separate `trim/playbackRate` segment; never apply one whole-shot playback-rate ratio and never alter the approved MP4 bytes.
6. Revalidate Summary-table equality, narration coverage, timing monotonicity, semantic A/V correspondence, exact parent-transition equality, transition bounds, action cadence, maximum holds, and the exact `visual_sequence_lock` digest. Stop if a shot is shorter than its locked transition or the replacement timing otherwise cannot fit the locked sequence; require another voice/speed or exit revoice through normal Transition Review and Storyboard Review.
7. Record phase `revoice_storyboard_retiming`, then present the new storyboard and replacement narration for a fresh Storyboard Review with phase `awaiting_revoice_storyboard_review`. On exact-byte approval set `revoice_storyboard_approved` and hand them back to `$run-knowledge-video` for revoice binding and assembly. Do not call `$produce-video-visuals`.

## Complete the workcard

- Apply the phase names below to the standard route. The revoice route uses the phase names in the preceding section while retaining the same exact-byte Review discipline.
- Write the final storyboard with the required opening Summary table followed by the unchanged complete detailed content.
- Produce exactly the two required user-facing workcard artifacts: the storyboard script and validated narration audio.
- In the standard route, use this exact phase order: `storyboard_construction → awaiting_visual_direction_review → visual_direction_review_approved → awaiting_visible_text_review → visible_text_review_approved → awaiting_transition_review → transition_review_approved → storyboard_qa_passed → awaiting_storyboard_review`. After direction, the complete visible-text batch approval, and Transition Review are current, and all bindings, Summary-table, narration-coverage, opening-schedule, timing-source, canvas, subtitle-normalization, and action-continuity-plan QA pass, recompute the storyboard file's exact-byte SHA-256 and atomically write the active path/SHA-256 with phase `storyboard_qa_passed`. Before presentation, atomically write `storyboard_review.status: pending`, phase `awaiting_storyboard_review`, the presented path/SHA-256 and presentation message/time; archive any prior approval in the superseded records and clear the active approved-version slot. Then present the complete storyboard script and validated narration audio and stop for the user's explicit decision.
- On a change request, atomically write `storyboard_review.status: changes_requested` and phase `storyboard_construction`, archive and clear the active approved-version evidence, then edit. Preserve unchanged direction and transition rows. If a shot's white-cat decision, structure, treatment, active route, or compatibility changes, reopen its Visual Direction Review row, recompute the direction map, invalidate the complete visible-text batch approval and that shot's visual asset family, and reopen affected Transition Review rows before final QA. If any visible-text mode/copy/placement or active row set changes, rebuild and re-present the complete visible-text map once; never request per-shot approval. If a boundary identity, kind, required option, or duration changes, return only that row to `pending`, regenerate the proposal checksum, and complete Per-Boundary Transition Review for the affected rows. Treat the result as a new storyboard version and rerun all bindings and QA before presenting it again.
- On explicit approval, reread the active storyboard file and recompute its exact-byte SHA-256. Only when it equals both the recorded active and presented SHA-256 may you record the approved path/SHA-256, the user's exact decision message/time, and set status `approved`.
- In the standard route, hand the storyboard to `$produce-video-visuals` only when the active, presented, and approved SHA-256 values all match, the complete `per-shot-visual-direction-review-v3` map equals the detailed/Summary direction fields, the approved `visible-text-batch-review-v1` equals every detailed/Summary text field, retired routes are absent, and every v3 transition row equals its approved mapping. In `retiming-only` mode, return for revoice binding and assembly.
